# 组合用模型：哪里能省、哪里不动

结论先说：

- **总调度和做票的子会话照旧用最强的模型（Opus 5.5），不动。** 路线判断、定判法、写代码、验收抽查都在这两类会话里，执行效果就是它们决定的。
- **能换便宜模型的只有两处**（这一期就这两处，做票的子会话一律不降），而且都有更强的一方在后面兜底：
  - **看门狗**：它的判断大多已经由 `csa patrol` 用代码做完了，它只照表办事，拿不准的一律报总调度；
  - **只读的子代理**：只负责找和摘，带 `文件:行` 回来，由主会话抽查。
- 看门狗换之前先跑两段试验：先拿固定的场景集离线比，再在线影子并跑；判法事先定好（第 5 节）。不过就不换。
- 省下的可能比价目表看起来少：这套系统的 token 大头应该是**缓存读取**，而 Opus 5.5 和 Sonnet 5.5 的缓存读取一样贵（第 2 节）。这是按假设算的，要用第 5 节第 0 步的实测校准。

这一篇的起因：用户转来一篇介绍 Claude 用法的帖子，问「组合用模型比只用 Opus 更划算」能不能用到这里。那篇帖子本身没有比较模型组合，和这里有关的只有两条：#3「只在要深想时开长思考」和 #17「提示缓存」。组合用模型这个想法本身值得做，下面按这套系统的实际情况算。

## 1. 价目（Anthropic 官方 API 价，每 100 万 token）

| 模型 | id | 输入 | 输出 | 缓存读取 |
|---|---|---|---|---|
| Opus 5.5 | `claude-opus-5-5` | $4 | $20 | $0.20 |
| Sonnet 5.5 | `claude-sonnet-5-5` | $2 | $10 | $0.20 |
| Haiku 5.5 | `claude-haiku-5-5` | $0.10 | $0.50 | 待核（见第 5 节第 0 步） |
| Fable 5.1 | `claude-fable-5-1` | $10 | $50 | $0.25 |

- 出处：Claude API 技能的模型表，2026-10-06 缓存的版本。
- Haiku 5.5 的价格只在单次请求 10 万 token 以内成立，超过以后是 $0.50 / $2.50。
- 缓存按模型分开：同一个会话中途换模型，前面的缓存就用不上了。
- 用订阅跑云端会话时并不按这个价扣钱，但所有会话共用账号的用量额度：哪个会话省一点，别的会话就能多走几步。`get_session` 里的 `cost_usd` 是按这个价折算的估值。

## 2. 钱花在哪

这套系统每走一步，会话都要带上全部上下文。上下文绝大部分是**前面已经缓存过的**，只有新的工具结果和这一步的输出按全价算。

粗算看门狗的**一次模型请求**（假设上下文 10 万 token 都已缓存，新输入 5 千、输出 1 千）。一轮巡检不止一次请求：跑 patrol、定 `send_later`、最后回一行，至少三次，每次都要把上下文再读一遍，所以一轮大约是下表的 3 倍以上：

| | 缓存读取 | 新输入 | 输出 | 一次请求 | 一天（144 轮 × 3 次） |
|---|---|---|---|---|---|
| Opus 5.5 | $0.020 | $0.020 | $0.020 | 约 $0.06 | 约 $26 |
| Sonnet 5.5 | $0.020 | $0.010 | $0.010 | 约 $0.04 | 约 $17 |
| Haiku 5.5，请求超过 10 万 token | 待核 | $0.0025 | $0.0025 | 待核 | 待核 |
| Haiku 5.5，上下文压在 9 万以内 | 待核 | 按 $0.10 / $0.50 档 | | 待核 | 待核 |

Haiku 那两行：10 万的缓存加 5 千新输入是 10.5 万，已经过了 10 万的线，按 $0.50 / $2.50 的档算。所以看门狗如果用 Haiku，换新的阈值要压到 9 万（[router.md](roles/router.md)「这条线的参数」）。

这几个数是估算：每次请求的缓存命中率、一轮有几次请求都还没实测，要拿第 5 节第 0 步的 `cost_usd` 校准。

从这张表能看出三件事：

1. **Opus 换 Sonnet 只省三分之一左右**（在上面的缓存假设下），因为缓存读取那一块一分没省。
2. **轮数和上下文长度可能和换模型一样值钱**：每少一次请求、上下文每短一截，省的是全部三列。看门狗从「每轮都看会话列表」改成只在 :00 和 :30 看（第二期 P1-5），上下文到 15 万就换新的，都不碰判断质量。这一条还是推断，实测前不当结论用。
3. **新开一个会话本身就有固定开销**：原来的使用中实测，一个什么都没做的新会话，光系统提示和工具说明就占约 6.7 万 token。所以「一张票一个子会话」要在票的边界换，不要切得更碎；看门狗换新的也不要太勤。

## 3. 每个角色用什么

| 角色 | 模型 | 为什么 | 怎么保证效果不降 |
|---|---|---|---|
| 总调度 | Opus 5.5（不动） | 定路线、定判法、验收抽查 | — |
| 子会话：所有做票的（实现、修 bug、调查、改文档） | Opus 5.5（不动） | 票的结果就是执行效果。gate 只能查写进去的检查，查不出「过了 gate 但做得差」，所以不靠 gate 兜底来降模型 | — |
| 看门狗 | 现在跟总调度一样；两段试验（第 5 节）过了换成 Haiku 5.5，不过就试 Sonnet 5.5 | 第一层判断 `csa patrol` 已经用代码做完了，看门狗照表推人 | 表里没有的情况、拿不准的，一律只记一笔并报总调度，不自己判（[watchdog.md](roles/watchdog.md)） |
| 只读子代理（读大日志、大 JSON、跨目录检索） | Haiku 5.5 或 Sonnet 5.5（Agent 工具的 `model` 参数） | 只负责找和摘，带 `文件:行` 和原文回来 | 主会话沿出处抽查关键的一两处；对不上就自己读，或者换同级模型重派 |
| 第一层巡检 `csa patrol` | 不用模型 | 纯代码 | — |

不做的：

- **不做自动升降级的级联**（先用便宜的，不行再换贵的）。级联要多跑一遍，还丢缓存。这里每个会话开的时候就定好模型，中途不换。
- **不给「纯机械」的票降模型**。第三期草稿里写过「没有 human 项、达标全由 gate 自动判的票可以用 Sonnet，gate 不过两次用 Opus 重开」，Codex 审查指出两点：它越过了「做票的子会话不降」的边界；「不过两次重开」本身就是级联，而且误过 gate 的结果发现不了。所以删了。以后真要做，单开一张票先做对照试验。
- **不用 Fable 5.1 省钱**：它比 Opus 贵，只在用户明说要最强模型时才用。
- **不调云端会话的思考强度**：`create_session` 只能选模型，选不了 effort。帖子 #3 说的「按需开长思考」在这里用不上。子代理的 effort 也不由我们定。

## 4. 落在哪里

- **票头 `model`**（可省）：`opus`、`sonnet`、`haiku`、`fable`，或完整的模型 id。总调度用 `create_session` 开子会话时照它填 `model`；没写就用这条线参数里的子会话默认模型（Opus 5.5）。这一期总调度只写 `opus` 或不写；这个字段先用来记录，给以后的对照试验用。和 `owner` 一样，**不算进判法**：换模型不报 `contract-changed`。写错了不让派。`csa ticket show` 会显示它。可以顺带写 `effort`，也不算进判法，只作记录。
- **这条线的参数**（[router.md](roles/router.md)）：子会话默认模型、看门狗模型、看门狗换新的上下文阈值。
- **看门狗的「拿不准就报」**（[watchdog.md](roles/watchdog.md)）。
- **子会话和总调度派只读子代理时的模型**（[worker.md](roles/worker.md) 第 9 条）。
- **缓存**（帖子 #17）：云端会话的缓存由平台自己做，我们能做的只有不打乱前缀：
  - 角色提示词开场发一次，中途不改；
  - 会话中途不换模型；
  - 消息只追加，短而固定格式（六种开头、600 / 1500 字上限本来就是这样）。

## 5. 换看门狗之前：两段试验

判法事先定好，跑完照判，不改。第一版只写了「在线并跑 12 轮」，Codex 审查指出：12 轮覆盖不到表里的大多数行；两个看门狗读的是同一份实时状态，现任的动作还会改变候选看到的东西。所以改成先离线、后在线两段。

0. **核可用性、校准成本**（一次）：用 `create_session` 开一个一次性会话，`model` 填 `claude-haiku-5-5`。开好以后看 `get_session`，`session_context.model` 和 `external_metadata.last_served_model` 都得是它。让它照 [watchdog.md](roles/watchdog.md) 跑一轮「无事」，记下这一轮的 `cost_usd` 增量和请求次数，拿来校准第 2 节。测完归档。开不出来，就换 Sonnet 5.5 重做这一步。
1. **离线比：固定的场景集**。把每个场景的输入写成文件：`csa patrol --json` 的输出、`list_sessions` 和 `get_session` 的结果，加上当时是几点几分。场景覆盖 watchdog.md 表里的每一行：
   - `runner-down`、`finished-unacked`、`over-estimate`、`pc-idle`（只出现一轮、连着两轮各一个）、`handed-in-waiting`、`contract-changed`、`auth-changed`（第一轮、连着第二轮）、`line-missing`、急停中；
   - 子会话 failed、30 分钟没活动但手上有作业、45 分钟没动静、`send_later` 说的时刻过了 15 分钟；
   - :00 时子会话超 40 万、自己超阈值；
   - 执行机连不上（第一轮、连着第二轮）；
   - 一个表里没有的情况；
   - 一轮无事。

   候选和现任（同一份提示词，只是模型不同）各自读同一套文件，写下要做的动作：推谁、发什么、报不报总调度、推不推手机。不连执行机，不发任何消息。
2. **离线判法**：
   1. 每个场景的动作都和现任一致，并且和表里写的一致：全部场景都对；
   2. 「表里没有的情况」那一个，候选只记一笔、报总调度；
   3. 没有一个场景多发消息（每轮最多三条）。
3. **在线影子并跑**：离线全过以后，候选看门狗一直停在「只观察」，和现任并跑 12 轮（2 小时）。它只读不写：不跑 `job_start`，不发消息，每轮只记下本来会做什么。
4. **在线判法**：
   1. 12 轮里每一轮，候选写下的动作和现任实际做的一致：12/12。读到的状态因为现任已经处理而不同的那几轮，按现任处理之前的状态比；
   2. 候选每轮的工具调用和现任一样多：每轮一次 `csa patrol` 和一次 `send_later`，:00 和 :30 多一次 `list_sessions`，:00 再多几次 `get_session`；
   3. 候选这 12 轮的 `cost_usd` 增量，比现任同期的增量低一半以上。
5. 都过：总调度换看门狗，新的看门狗用候选模型，照常先只观察两轮再接手。有一条不过，照实记下来：Haiku 不过就换 Sonnet 从第 1 步再来；Sonnet 也不过就不换。
6. 换了以后也盯着：48 小时里，凡是总调度或用户先于看门狗发现的跑偏，都算一次漏报。有一次就换回去。

只读子代理不另做试验：主会话本来就要沿出处抽查。抽查对不上的，记进 run log。同一类读取连着两次对不上，那一类就改用同级模型。
