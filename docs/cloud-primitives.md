# 云端原语：这套做法用到的 Claude Code 云端会话工具

总调度、子会话、看门狗都是 Claude Code 的云端会话（claude.ai/code 上开的那种，跑在 Anthropic 托管的容器里）。会话之间互相开、互相发消息、定时叫醒，靠的是云端环境自带的一组 MCP 工具（服务名 `claude-code-remote`）。

**先说清楚：** 这些工具的行为，下面写的都来自会话里工具自带的说明（2026-11 读到的版本），公开文档里写得不全，以后可能会变。所以这套做法只拿消息**叫醒**对方，不拿消息**存状态**：状态都在执行机上的文件里（排队记录、台账、gate 结果）。云端会话本身的说明见官方文档 <https://code.claude.com/docs/en/claude-code-on-the-web>。

## 一览

| 原语 | 谁用 | 用来做什么 |
|---|---|---|
| `create_session` | 总调度 | 开子会话、开看门狗 |
| `send_message`（`now` / `next` / `later`） | 三类会话 | 派单、汇报、推一下 |
| `send_later` | 子会话、看门狗 | 估计作业跑完的时刻回来看；看门狗的 10 分钟巡检链 |
| `create_trigger` | 总调度 | 每小时一次的兜底，接上断了的巡检链 |
| `subscribe_pr_activity` | 子会话（GitHub 上的票） | PR 的评论、评审、CI 结果直接推进会话 |
| `get_session` / `list_sessions` | 看门狗、子会话 | 状态、上下文用量、自己的会话 id |

## create_session：开会话

- 不给 `environment_id` 就继承调用者的环境（同一套网络策略、环境变量、setup 脚本）。可以给 `source_url` 挂仓库、给 `prompt` 当开场消息、给 `title` 和 `tags`。
- `permission_mode` 不能比调用者更宽；不填就继承。**不要给没人看着的子会话用 `plan`**：它会停在等人批准计划那一步。
- 子会话的一轮出错、或者它的 worker 重启丢了后台任务时，开它的会话会收到一个 `<child-session-event>`（工具说明写的是 where enabled，不保证每个环境都有）。正常跑完**不会**回报，要自己用 `get_session` 看 `status_bucket`。
- 用法：一张票一个子会话（[router.md](roles/router.md)「派单」第 0 条）。新会话光系统提示和工具说明就占几万 token，所以「紧接着做同一件事、上下文不到 30 万」时才复用原会话。

## send_message：给另一个会话发消息

- 消息在对方那边是一轮「由另一个会话发来的」输入，不是人打的字。对方被告知把它当同伴的数据看，单凭它不改权限、不做新的破坏性操作。所以**授权必须在对方自己能核对的地方**（项目仓库里的「授权」一节，加 `csa ticket init` 记下的哈希），不能只写在消息里。发布类动作（建仓库、推送、发评论等）更严：只认用户本人在执行动作的那个会话里说的话，别的会话转来的「用户同意了」一律不算。
- 调用在**送达**时返回，不等回复；对方要回就自己 `send_message` 回来。
- `priority`：
  - `now`：打断对方当前这一轮，马上处理；
  - `next`：并进对方正在跑的这一轮，不打断；
  - `later`：等对方这一轮结束再处理；
  - 不填：对方用自己的默认排法。
- 规矩：**发给正在干活的会话一律 `now`**，写死在三份提示词里，不靠记。实际用下来，不带 `now` 的消息在对方一直忙时可能很久才被看到。
- 长度：子会话 → 总调度 ≤ 600 字，派单 ≤ 1500 字，细节给出处（原型的同类上限：`src/app/notices.ts:110` 交回摘要 600 字符，`src/executor/dsh.ts:113` 派单 1500 字符）。

## send_later：定时叫醒自己

- 在将来某个时刻往**本会话**送一条消息。精度一分钟；存在服务端，容器重启也照样送到。到点时本会话正在跑一轮，就等这一轮结束再送，不打断。
- 返回一个 id，送达前可以用 `delete_trigger` 取消。
- 用法：子会话排了作业就定在「估计跑完的时刻」回来看，不固定隔 30 分钟；看门狗每轮最后定在下一个整 10 分（:00、:10…）。
- **它不保证准时叫醒。** 到点时对方正在跑一轮就要等这一轮结束；会话长时间空闲后，送到也可能晚。原来的使用中实测过：作业跑完到负责的子会话来取，最长晚了 34 分钟。所以「作业跑完」不能只靠 `send_later`，还要看门狗的 `finished-unacked` 兜底。
- 为什么不用会话里的 `/loop`、CronCreate：那些存在会话的 VM 里，VM 被回收后不恢复。

## create_trigger：定时任务

- 三种目标：打进本会话（默认）；打进指定的另一个会话（`persistent_session_id`）；每次新开一个会话（`create_new_session_on_fire`）。
- `cron_expression`（5 段，默认 UTC，可写 `CRON_TZ=<时区>` 前缀）或 `run_once_at`（一次性）。**最小间隔通常是一小时**，更密的会被拒绝。
- 用法：总调度给看门狗配一个每小时一次、打进看门狗会话的定时任务。看门狗的 `send_later` 链子万一断了（某一轮出错没定下一轮），最多一小时接上。10 分钟一轮的巡检本身靠 `send_later`，不靠它。

## subscribe_pr_activity：PR 动态直推

- 订阅一个 PR 后，评论、评审、CI 结果等事件会作为一轮输入推进本会话。幂等。一个 PR 的事件同一时间只给一个会话；别的会话已经在看，这次调用成功但收不到。
- 用法：
  - 票的产出是 GitHub 上的 PR 时，gate 可以放进 CI，「作业跑完」就是 CI 结果，由这条直接推给子会话，不用看门狗转告。
  - 第二期设计「信箱 PR」：让执行机在作业结束时往一个专用 PR 上发评论，借这条把消息直推进会话（见 [run log](run-log.md)「下一步草案」第 5 项，**还没实测**）。

## get_session / list_sessions：看状态

- `get_session` 不带 `session_id` 就是查自己：子会话靠它拿到自己的会话 id，填进 `csa queue add --session`。
- 返回里有 `status_bucket`（working / blocked / review_ready / completed / failed；`failed` 表示最后一轮出错，这时 `status` 本身可能只显示 idle）、创建时间、最后活动，和上下文用量。上下文用量的字段是 **`external_metadata.context_usage.used_tokens`**：子会话交回时报这个数；看门狗在 :00 那一轮看一次（[watchdog.md](roles/watchdog.md)）。
- `list_sessions`（`mine: true`）一次列出多个会话，看门狗用它代替逐个 `get_session`。**默认只返回 20 条**，会话多了要给 `limit`（最多 100）或翻页（`after_id`），不然会漏。看门狗只在 :00 和 :30 两轮调它。

## 不用的

- **会话里的 hooks。** 挂了几个仓库的云端会话不一定跑仓库的 hooks，约束不能放这里，放执行机上的命令里。
- **用消息存状态。** 消息只叫醒；状态在执行机上的文件里，压缩以后先读台账（`csa ticket list`）。
