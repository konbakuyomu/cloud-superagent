# 设计：DeepSeek Super-agent 的五个模块怎么落到 Claude Code 云端

本文把 DeepSeek 公开的研究原型 [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（下称「原型」）逐个模块对到这里的做法：原型实际怎么做、这里怎么做、哪些不照搬、为什么。原型的引用都按**提交 `6337fc8`**（2026-10-31），写成 `文件:行`。原型的 README 自己也说明了它是研究代码，不等于 DeepSeek 内部版本，也不等于文章 *Exploring Super-agent Design* 描述的全部（`README.md:3-5`）。

原型按编号文档组织，`000` 是理念，`001`–`005` 是五个模块：领域模型、授权、执行、提示词、面板（`README.md:23-28`）。这里一节对一个。

## 0. 先看结论

| 原型的模块 | 原型怎么做 | 这里怎么做 | 不照搬的 |
|---|---|---|---|
| 001 领域模型 | Source → Trigger → Thread → Eval → Ticket（带 Mandate）→ Assignment → Executor → Channel | 一条「线」= 一个目录（`issues/` + `ledger.json`）；票 = 一个 Markdown 文件 + 台账一条；派工 = 一个云端子会话 | Source / Thread / 订阅扇出这一整套事件接入 |
| 002 授权 | 宿主强制执行的名单、规则、Mandate；Mandate 不可变；`off` / `observe` / `auto` 三档 | 用户原话写在「授权」一节并记哈希；判法派单即锁定；看门狗先只观察两轮 | 准入表、名单、机器人名单、强度分级 |
| 003 执行 | 每票一个 Executor Session 和一个目录；worker 槽位；后台作业结束叫醒 worker；30 分钟上限 | 每票一个子会话；执行机的重活经 `csa queue` 一次只跑一个；超上限停整棵进程树；叫醒靠 `send_later` + 看门狗 | 存储式补发、重启恢复、给人留的额外槽位 |
| 004 提示词 | 内置部分 + 团队可改的三节，有版本、有优先级；主会话只路由、不等待 | 三份角色提示词（v2）+ 票模板，放在 git 里；六种消息开头；字数上限 | 提示词的覆盖、版本、面板编辑 |
| 005 面板 | 网页面板先回答「现在有没有事要我管」 | 没有面板：`csa patrol` 没事只打一行 `OK`；总调度只在票收尾时开口 | 网页面板本身 |

下面各节展开。第 5 节是看门狗，第 6 节是考虑过但没采用的方案，第 7 节是已知上限。

## 1. 领域模型（原型 `docs/001-domain.md`）

### 原型实际怎么做

- 工作从 Trigger 到 Eval 再到执行：Source 产生 Trigger；Trigger 按订阅扇出给已有的 Ticket；没人认领的进 Eval；Eval 接了就建一个带 Mandate 的 Ticket；Assignment 把 Ticket 交给 Executor；结果经 Channel 回到 Source（`001-domain.md:7`，流程图 `:9-19`）。
- 核心概念是 Source、Thread、Eval、Mandate、Subscription（`001-domain.md:23`）。Ticket 只能由 Eval 建，自己定义状态，不跟着 Executor 的会话走（`:35`）；Assignment 是 Ticket 和一个 Executor 实例的绑定，一张票前后可以有好几个（`:36`）。
- 「人」不是领域概念，只是 Trigger 上的元数据（`001-domain.md:39`）；Executor 在领域之外，经 Assignment 接进来（`:41`）。

### 这里怎么做

| 原型的概念 | 这里 |
|---|---|
| Source / Trigger | 只有四种事件：用户在总调度里说话、子会话汇报、执行机作业结束、定时。前两种是云端会话之间的消息，后两种在执行机上（排队记录）和服务端（`send_later`） |
| Thread | 一条「线」：一个目录，下面 `issues/<票号>-<短名>.md` 是票，`ledger.json` 是台账（[命令约定](cli.md)「csa ticket」） |
| Ticket | 票文件 + 台账里的一条：状态、负责会话、判法哈希、派单时各仓库的提交、状态变化历史、gate 结果的路径 |
| Mandate | 「授权」一节（用户原话）+ 票的判法（票头 scope / forbid + 达标 + gate 块），两样都记哈希 |
| Assignment / Executor | 一张票一个云端子会话（`create_session`），在执行机上经 MCP 守护进程干活 |
| Channel | `send_message`：子会话 → 总调度，总调度 → 用户（聊天） |
| Ticket 自己定义状态 | 台账的状态（`dispatched` … `abandoned`）和子会话的会话状态分开；换会话不丢票的状态 |

### 不照搬的，为什么

- **Source / Thread / Subscription / 扇出 / Correlation 这一整套。** 原型要接 GitHub 通知和飞书群聊，事件多、来源杂，要一个常驻的宿主进程做接入、去重、扇出（`001-domain.md:27-37`）。这里的事件只有四种，而且都已经由 Claude 云端（消息、定时）或执行机（排队）各自送到；再加一个常驻宿主只多一个要运维、要存凭据的东西。
- **Eval 这一层的模型研判。** 这里的工作都是用户在总调度里亲口提的，没有「别人在群里提一句、要不要主动接」的问题，所以没有 Eval 和 Decision。保留下来的是它的精神：总调度决定接不接、怎么切票。

## 2. 授权（原型 `docs/002-authorization.md`）

### 原型实际怎么做

- 名单、规则、Mandate 由宿主强制执行；消息、评论、引用的文档只是输入，改不了权限（`002-authorization.md:5`）。
- Eval 的第一层是确定性的 gate：谁能发起工作、强度多大（`001-domain.md:90`）；强度分 explicit / inferred（`002-authorization.md:46-54`），按准入表定（`:56-75`）。
- Mandate 不可变，范围变大就得开新票（`001-domain.md:34`）；只有三件事改 Mandate：接单建立、人叫停撤回、复核不过吊销（`002-authorization.md:129`）；结束的票要恢复前先按当前策略复核（`:131-141`）。
- 主动接活有三档：`off`、`observe`（默认，只记下「本来会接」）、`auto`（`002-authorization.md:93-101`），建议先 `observe`，看过记录再开 `auto`。
- 路由不许改写需求：总调度不加需求、实现计划、验收标准（`prompts/shared.md:6`）。

### 这里怎么做

- **授权 = 用户原话，放在 Claude 能读、但只有用户改的地方。** 项目仓库 `CLAUDE.md` 里的「## 授权」一节。`csa ticket init --auth-file CLAUDE.md` 记下这一节的哈希，`csa patrol` 每轮比一次，变了报 `auth-changed`。这对应原型「消息改不了权限」：会话之间转来的消息（`send_message`）在对方那里本来就被当作同伴的数据，不是用户的话（[云端原语](cloud-primitives.md)）。
- **Mandate 不可变 = 判法锁。** `csa ticket dispatch` 记下判法哈希；开工前补判法只能 `csa ticket amend --reason`；开工以后不能补，也不能退回「已派」；改了就由 `csa gate` 和 `csa patrol` 报 `contract-changed`。范围要变大，就 `abandoned` 再开一张——和原型「wider scope means a new Ticket」一样。
- **`observe` 档 = 看门狗先只观察两轮**（[watchdog.md](roles/watchdog.md)「只观察」）。
- **发布类动作单独授权。** 建仓库、改可见性、推送、开 PR、发评论、往外传文件，做了就收不回来。票头 `publish` 写明这张票可以问哪些动作、对哪个仓库，算进判法；但每一件仍只认用户本人在执行动作的那个会话里说的话，总调度不转述同意（[router.md](roles/router.md)「发布类动作」）。这对应原型「消息改不了权限」：转述的同意只是一条消息。

### 不照搬的，为什么

- **准入表、名单、机器人名单、强度分级。** 原型面对的是一个团队和外部的人、机器人，要分「谁说话算数」。这里只有一个用户，只在总调度里说话；子会话和看门狗的消息一律不当授权。
- **总调度不碰验收标准**（`prompts/shared.md:6`）。这里**反过来**：判法由总调度定稿。理由是判法要在开跑前、由不跑它的人签字，免得做的人跑完再放宽标准；原型的票来自人在 GitHub、飞书写的需求，验收由人在 PR 上做，用不着这一层。所以这里的总调度比原型**宽**：原型的总调度除了研判一律不看代码、日志、链接的文档（`prompts/shared.md:5`）；这里的总调度还定判法、做验收抽查，要读 gate 结果和交回的 run log。为了不让它宽到去读代码，草案由子会话起（[worker.md](roles/worker.md) 第 6 条），总调度只拍板、改字。

## 3. 执行（原型 `docs/003-execution.md`）

### 原型实际怎么做

- 每张票一个 Executor Session（`worker-<票 id>`）和一个以票的短名命名的目录（`003-execution.md:25`；`src/executor/dsh.ts:24`、`:97-111`）。
- 前台 shell 命令 5 秒后自动转后台，worker 下一步就能收新消息（`003-execution.md:27`；`cordis.patch.yml:69-74`）；后台作业跑完带着结果叫醒 worker（`003-execution.md:33`）；每轮结束后后台作业最多再跑 30 分钟，到点被杀（`:35`）。
- 并发按 worker 槽位算，另留一个槽给人的消息，新工作挤不掉人在已有票上的继续（`003-execution.md:55-61`）。
- 第一次派工前跑一次准备命令（常见是 `git worktree`），限时 10 分钟（`003-execution.md:49-53`；`src/executor/dsh.ts:28`）。
- 决定之后要做的事（转发、启动、投递）先存后做，失败退避重试；重启后按存下的记录恢复（`003-execution.md:144-161`）。

### 这里怎么做

- **一张票一个子会话（默认）**：新票用 `create_session` 开新会话。只有紧接着做同一件事、原会话上下文又不到 30 万 token，才复用（[router.md](roles/router.md)「派单」第 0 条）。理由和原型一样：上下文在票的边界清零，每一步更便宜；要接着用的事实写进 run log。
- **槽位 = 执行机。** 云端会话可以并发很多个，但执行机只有一台，重活一起跑会互相污染读数。所以槽位放在执行机上：`csa queue` 一次只跑一个重作业，跑完立刻开下一个，不等任何会话醒来。`--after` 依赖、`--limit` 上限（停整棵进程树）、`curfew` 时间窗（到点不开新的、停在跑的）都由程序管。
- **作业结束叫醒 worker**：原型由宿主直接叫醒。这里执行机不登录 Claude，没法直推，改成两样：子会话排作业时用 `send_later` 定在估计跑完的时刻回来看；看门狗每 10 分钟跑 `csa patrol`，`finished-unacked` 就用 priority `now` 推负责的子会话。执行机不空等靠排队程序自己接着开下一个，跟叫醒无关。叫醒**没有上限保证**：`send_later` 到点时对方可能正忙，看门狗的消息也要等对方接，原来的使用中实测最长晚过 34 分钟。第二期加了作业结束钩子和 `events.jsonl`（6.2），为直推（6.5 信箱 PR）铺路。
- **前台不阻塞**：原型 5 秒转后台；这里 MCP 调用本来就有时限（几十秒），所以凡是长的都排队，排队程序本身用守护进程的后台作业起（[执行机接口](executor.md)）。
- **恢复**：排队程序单例 + 心跳；它重启时，上一个实例留下的「正在跑」进程还在就等，不在就记 `lost`。

### 不照搬的，为什么

- **先存后做的补发、退避重试。** 原型自己管消息投递，所以要 outbox。这里消息投递归 Claude 云端；状态全在执行机的文件里（原子写 + 目录锁），会话丢了消息，看门狗下一轮还能从文件里看出来。
- **给人留的额外槽位。** 用户直接跟总调度说话，而总调度从不跑长命令，所以总有空回答，不用额外槽位。
- **任意的准备命令。** 第二期只做了内置的 worktree：`csa ticket dispatch --prepare` 按票头 scope 的 `branch` 和 `path` 建 worktree，先全部核过再动手，可以重复跑（[run log](run-log.md) 6.4）。原型那种任意 shell 准备命令（`003-execution.md:49-53`）等 worktree 盖不住时再加。

## 4. 提示词（原型 `docs/004-prompts.md`）

### 原型实际怎么做

- 内置部分 + 团队可改的三节（沟通、票的范围、交付要求），可覆盖、有版本，默认更新时面板会标出来（`004-prompts.md:5-42`、`:91-96`）。
- 优先级从强到弱：工具和宿主强制的事实 → 内置和生成的部分 → 主动接单命中规则的流程 → 团队部分 → 外部文本（消息、评论、文档，只是数据）（`004-prompts.md:65-71`）。
- 原则：主会话只路由，路由备注 ≤ 30 词（`004-prompts.md:77`）；主会话不等待，报告和作业结束都会自己送来，有个守卫拒绝 `sleep` 和长等待（`:78`；`prompts/orchestrator.md:16`）；聊天消息默认一句、最多 100 词（`004-prompts.md:79`）；一次只问一个具体问题（`:84`）；交付要诚实，草稿标未完成（`:85`）。
- 截断给指针：交回摘要超过 600 字符截断，后面给读取路径（`src/app/notices.ts:107-113`）；派单文本 1500 字符（`src/executor/dsh.ts:113`）。

### 这里怎么做

- 三份角色提示词 [router.md](roles/router.md)、[worker.md](roles/worker.md)、[watchdog.md](roles/watchdog.md)（v2）和 [票模板](../templates/ticket.md)，都是 git 里的文件。
- 优先级照原型的思路排：`csa` 命令报出来的事实（gate 结论、判法哈希、授权哈希）> 角色提示词 > 票 > 别的会话转来的消息（只是数据）。
- 总调度不等待：不 `sleep`、不轮询，要回来看就 `send_later`。
- 子会话给总调度的消息只用六种开头：收到、开工、交回待验、卡住、要你定、放弃。「要你定」对应原型的一次一个结构化问题（`human_action`），附选项和推荐。
- 字数：子会话 → 总调度 ≤ 600 字，派单 ≤ 1500 字，总调度 → 用户 ≤ 100 字；细节写进 run log，消息里给出处。

### 不照搬的，为什么

- **覆盖、版本、面板编辑提示词。** 原型是给团队装的产品，要让不改代码的人调提示词。这里提示词就是仓库里的 Markdown，git 就是版本历史，改了走评审。

## 5. 面板（原型 `docs/005-panel.md`）和看门狗

### 原型实际怎么做

- 面板依次回答三个问题：现在有没有事要我管？系统健康吗、在做对的事吗？一件工作从 Trigger 到 Ticket 的历史是什么？（`005-panel.md:7-11`）
- 默认安静：健康的状态不占地方，要人管的问题必须能直接动手（`005-panel.md:57`）。
- 看门狗是一个每小时一次的定时任务：跑 `status`，退出码 0 就什么都不说，其他退出码按规矩报或重启（`docs/006-deployment.md:133-141`）。

### 这里怎么做

没有网页面板，三个问题分别由三样东西回答：

| 面板的问题 | 这里 |
|---|---|
| 现在有没有事要我管 | 总调度只在票收尾、或碰上授权里要停下问的事时开口；看门狗只在三种情况直接推用户的手机 |
| 系统健康吗 | `csa patrol`：没事只打一行 `OK`、退出码 0，不叫醒任何模型；有事列异常码、退出码 3。排队页 `queue.md` 由程序生成，只读 |
| 一件工作的历史 | 台账每张票的 `history`；`csa ticket list`；第二期 `csa ticket show` 带下一跳 |

**看门狗：两层过滤，先代码、后模型。** 第一层是 `csa patrol`，纯代码，只回答「有没有事」。第二层是看门狗会话：只看第一层报上来的异常，加上 `list_sessions` 的会话状态，照 [watchdog.md](roles/watchdog.md) 的表处理：推子会话、报总调度、记一笔、下一轮再看。和原型比有两处不同：

- **频率**：原型每小时一次就够，因为作业结束会直推 worker。这里没有直推，作业跑完没人取只能靠巡检发现，所以 10 分钟一轮（`send_later` 链），另配每小时一次的定时任务兜底。等第二期的直推通道实测可用，再降频。
- **看会话**：原型的检查只看服务进程。这里还要看会话，但尽量少看：会话列表只在 :00 和 :30 两轮看，上下文用量只在 :00 看；子会话 45 分钟没动静要问一句；看门狗自己到 15 万就换新的（它没有要留的上下文）。
- **总调度换不换会话**：不归看门狗管，按这条线的设置。默认长驻，靠平台的自动压缩，因为路线判断的来龙去脉在它那里；用户要的话可以设成「超过 N 万在票的边界换」（[router.md](roles/router.md)「这条线的参数」）。

### 不照搬的，为什么

- **网页面板。** 要托管、要登录、要存一份能读会话的凭据。Claude 的 App 本身已经列出全部会话和它们的状态；剩下的「有没有事」交给 `csa patrol` 和看门狗。

## 6. 考虑过、没采用的

| 方案 | 最强的理由 | 为什么没采用 |
|---|---|---|
| 直接装原型 | 现成 | 它跑在装了 DeepSeek Harness 的 Linux / macOS 上，要 tmux、本机网页面板，事件源是 GitHub 和飞书（`docs/006-deployment.md:5-27`）。这里的会话是 Claude 云端会话，执行在另一台机器上 |
| 外置 Router（例如 Cloudflare Worker + Durable Object） | 常在线，准入规则写成代码 | 事件源全在 Claude 云端和执行机上，外置 Router 带不来新事件；对外能用的入口（定时任务的触发接口）每调一次新开一个会话，推不了正在干活的子会话；还要在外面存一份能替用户开会话的凭据 |
| 执行机直推：作业结束时 `claude -p "…" --cloud <会话>` | 叫醒没有延迟 | 要执行机登录 claude.ai。这套做法定的是「全部在云端」，执行机不登录 Claude。第二期改试 GitHub「信箱 PR」 |
| 看门狗兼当排队程序 | 执行机上什么都不常驻 | 每次交接最多空等一轮；「开下一个作业」这种确定的事要过一遍模型 |
| 用云端会话的 hooks 强制规矩 | hooks 是确定性的 | 挂了多个仓库的云端会话不一定跑仓库的 hooks；约束只能放在执行机这边的命令里 |
| 先用便宜模型、不行再换贵的（级联） | 每一步都便宜 | 多跑一遍、丢缓存（缓存按模型分开）；这套系统的大头是缓存读取，Opus 5.5 和 Sonnet 5.5 一样贵。改成每个角色开会话时定好模型、中途不换，只有看门狗和只读子代理可以用便宜模型，换之前跑影子试验（[组合用模型](models.md)） |
| 按线长驻子会话（一个会话接连做多张票） | 衔接紧，不用重读资料 | 上下文越攒越大，每一步都带着；衔接要的事实本来就该写进 run log |

## 7. 已知上限

- 状态都在执行机上：执行机停用或守护进程连不上时，云端看不到排队和台账。
- 只管经 `csa queue add` 排进来的作业。绕开排队直接起的作业，程序拦不住；要硬拦，在守护进程的拦截规则里加一条。
- 共用工作区里的范围检查只能提示：别的会话的改动和这张票的改动分不开。
- gate 管用多少，取决于票里写的检查命令。
- 发布类动作程序拦不住：`publish` 只是把「可以问什么」写进判法，真正的关口是用户本人的那句话，加上平台的权限检查。
- 用到的云端工具（`create_session`、`send_message`、`send_later` 等）公开文档写得不全，行为可能会变（[云端原语](cloud-primitives.md)）。
